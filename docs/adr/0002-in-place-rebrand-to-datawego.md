# Rebrand cloud-mail from EDMF to DataWeGo by in-place mailbox rename, not data migration

**Status: accepted — executed 2026-10-08** (see `docs/plans/2026-10-08-2300-feat-edmf-to-datawego-cutover-plan.md`).

The single production `cloud-mail` deployment (one Cloudflare account; Worker + D1 `cloud-mail-db` + R2 `cloud-mail-r2` + KV, all bound by fixed IDs in `wrangler.production.toml`) served the EDMF org on `edmf.nl`. We decided to repurpose it for DataWeGo instead of standing up a new deployment or moving resources: keep every binding ID untouched, temporarily accept both domains (`domain = ["edmf.nl", "datawego.nl"]`), rename every mailbox in place `@edmf.nl` → `@datawego.nl` (local-part preserved) with history and R2 attachments intact, then shrink to `domain = ["datawego.nl"]` and `admin = "admin@datawego.nl"`, and finally drop the `mail.edmf.nl` custom domain and EDMF mail handling. Alternatives considered: fresh DataWeGo deployment with mailbox export/import (real data migration for zero benefit, since D1/R2 never leave this account), and permanent dual-domain coexistence (contradicts "no longer serving EDMF").

**Consequences:**
- Admin status is derived from the configured `admin` address, not a DB flag — the D1 rename and the `env.admin`/`env.domain` var changes must land in the same cutover window, renaming rows before (or together with) shrinking `domain`, or every `@edmf.nl` login — admin included — is rejected mid-flight.
- Addresses are stored as strings in several tables (`user.email`, `account.email`, `email.send_email`/`to_email`); the rename is UPDATEs over all of them. The v3.7 `email_search` triggers mark the search index dirty on those updates, so reindexing is automatic.
- R2 needs no re-upload: attachment keys are content hashes, not addresses.
- EDMF-era data stays in the same D1/R2 (renamed, not deleted); any future "clean EDMF data" step is now a no-op by choice.
- Outbound sending stays on the code's existing Resend path (per-domain `resendTokens`; note the settings row is *stored in* the KV `setting:` key, not merely cached there — `settingService.query()` has no D1 fallback, so the KV entry is runtime-authoritative and only `refresh()`, triggered by saving System Settings in the admin UI, rebuilds it from D1); we deliberately did **not** switch to a Cloudflare `send_email` binding during the cutover. The Brevo DKIM/SPF records on `datawego.nl` belong to other DataWeGo services and are not part of cloud-mail's mail flow.
- `r2Domain` follows a conditional rule: keep the current value if it is brand-neutral (e.g. an `*.r2.dev` public dev URL — keys are content hashes and `{{domain}}` placeholders re-point all historical emails automatically); replace it with a DataWeGo custom domain on the same bucket (e.g. `mail-files.datawego.nl`) if it contains any EDMF branding. The current value is in the D1 settings row (KV-cached), not in the repo, so it is verified during cutover.
- `jwt_secret` is rotated in the same cutover window: every token embeds only `{userId, uuid}` and sessions live 30 days in KV, so without rotation old sessions would keep authorizing with cached `@edmf.nl` identities long after EDMF is "gone". A one-time forced re-login into renamed accounts is the accepted cost.
- Off-boarding is a hard cut: no grace period for inbound `@edmf.nl` mail; `edmf.nl` leaves the managed-domain list, `mail.edmf.nl` is removed, and EDMF's Email Routing/MX are retired in the same window (or a dated handoff instruction is given to whoever controls the `edmf.nl` zone).
- The rename touches identity columns only (`user.email`, `account.email`, `email.send_email`/`to_email`/`recipient`/`cc`/`bcc`, and settings-row domain references); message bodies, attachment keys, and Message-IDs are historical wire data and keep their `@edmf.nl` strings. "Rename in place" therefore means EDMF becomes *inactive*, not *invisible* — a literal scrub of all EDMF text from D1 would require body rewrites we explicitly reject.
- `calendar_response.organizer` is rewritten only where a data check (`LIKE '%@edmf.nl'` matching renamed users) shows a live RSVP/dispatch consequence; external organizers' rows are left as received.
